# 05. VA portals

Owner: workstream F for the queues and route files under `src/app/va/`; the record screens are the feature components owned by workstream D and E, rendered with a narrower `capabilities` object. Every route needs `user_roles.role = 'va'`, an active `staff_profiles` row with the matching `va_function`, and a completed two-step sign-in. A VA with two functions (cover shifts) sees both queues with a switcher.

Sources: the 20 operating procedures, the VA hiring package (roles, scorecard, trust controls), `docs/permissions.md`.

## 1. The queue model

Each function has one home: its queue. A queue is the open `tasks` rows for that function, ordered by priority then `due_at`. Tasks are created by the system when an event needs a person; staff rarely create them by hand.

### 1.1 Queue screen (all four functions)

| Item | Detail |
| --- | --- |
| P layout | Tabs: Mine, Unassigned, Waiting. Cards: title, record (booking number or plate), due time with a countdown, priority, procedure number. Tap opens the task sheet |
| D layout | Left rail (function sections), queue table in the middle, the open task in a `SidePanel` with the record's working screen embedded, so the task is done without leaving the queue |
| Columns | Priority, Task, Record, Due, Waiting since, Assigned to, Procedure |
| Filters | Mine, unassigned, task type, due today, overdue, escalated |
| Realtime | Subscribes to `tasks` for the queue; new tasks appear without a refresh; a red count badge sits on the browser tab |
| Empty | "Queue clear." with the next scheduled items (for example tomorrow's pickups) |

### 1.2 Task sheet

| Element | Detail |
| --- | --- |
| Header | Title, due, procedure link (opens the procedure text from `content/procedures/` in a drawer) |
| Body | The working screen for that task type (sections 2 to 5) |
| Buttons | Take it (`assignTask` to me), Done (`completeTask`; refused until the task's completion rule holds, for example a verification task needs every driver verified or rejected), Waiting (`setTaskWaiting` with a reason and a wake time), Escalate (`escalateTask`: reason required, chosen from that procedure's "Escalate to admin when" list or free text; sets `escalated`, moves a copy to the `admin` queue, emits `staff_approval_needed` immediately, not digested), Hand over (`reassignTask` to a colleague from `staff_directory`) |
| Notes | A thread on the task, stored as `messages (channel = 'portal', related_table = 'tasks')` |

## 2. `/va/finance` Finance and Billing

Sections in the left rail: Queue, Charges, Deposits, Refunds, Tolls and tickets, Owner invoices, Statements, Payouts (prepare), Insurer invoices, Reconciliation, Fleet report, Turo trips.

| Capability | Finance VA | Enforced by |
| --- | --- | --- |
| Read bookings, payments, line items, deposits, refunds | Yes | Row-level security policies |
| Renter records | Only "in window" (live booking, 90 days after, open task, or a logged 24-hour lookup with a reason via `app.staff_open_renter()`) | `app.va_sees_renter()` |
| Card numbers, processor tokens, bank account numbers | Never | No policy on the secrets tables |
| Price findings and issue a statement | Yes; damage lines need an admin | `03-admin.md` section 11.3; escalation rule in procedure 5 |
| Release a deposit, release a refund from the cancellation table | Up to `staff_profiles.single_limit_cents` (starts at $0, so everything goes to approvals in month one) | `app.guard_deposit_release()`, `app.guard_refund_approval()` |
| Any other refund | Request only | Same guards |
| Tolls and tickets | Full: enter, import, match, charge | `10-tolls-tickets-damages.md` |
| Owner invoices | Read; record an e-Transfer payment | Policy |
| Owner deductions | Create, except "agreed in writing" | Policy |
| Owner statements | Read drafts, add notes, cannot approve | `owner_statements` policy |
| Payouts | Prepare to "pending approval"; never approve | `app.guard_payout()` |
| Change a payee's bank details | Never | Admin-only table |
| Export | Statement and report exports for the current task; no customer list | No list view exists |

Working screens are the admin components from `03-admin.md` section 11 and `11-statements-and-reports.md` with the approve buttons replaced by "Send for approval".

**Reconciliation (`/va/finance/reconciliation`).** Daily: Stripe payouts (from the `reconcile` job) against `payments`. Columns: payout date, amount, payments matched, unmatched amount. An unmatched item opens with candidate payments; `matchPayoutItem` links them; anything still unmatched escalates to an admin at the closing check.

**Turo trips (`/va/finance/turo`).** Enter or import (CSV) trips: trip reference, vehicle, start, end, gross (trip price plus distance fees), Turo's fees, delivery and extras (company), damage payment (owner). `saveTuroTrip` computes `revenue_share_cents` with `calc_bps()` (the table's check constraint verifies it) and sets `statement_month`.

## 3. `/va/fleet` Fleet Operations

Sections: Queue, Calendar (master calendar: read, create blocks, schedule jobs; drag is limited to blocks and field jobs), Today (handovers and returns board), Field jobs, Photo reviews, Vehicles, Listings, Tracker, Incidents, Onboarding (after signature), Daily checks.

### 3.1 Today board

Two columns, Handovers and Returns, each row: time, car, renter first name, place, field staff member and whether they acknowledged, readiness chips (verified, coverage, deposit, car ready, tracker reporting). A row missing a field staff member or an acknowledgement 2 hours before is red. Buttons: Assign (`createFieldJob` or `reassignFieldJob`), Message field staff (portal notice plus email), Open booking.

### 3.2 Dispatch a field job

| Label | Type | Validation | Stored |
| --- | --- | --- | --- |
| Kind | select: handover, delivery, return check-in, pickup from renter, detail, photo shoot, tracker install, tracker removal, registry run, recovery, other | Required | `field_jobs.kind` |
| Vehicle | select | Required | `vehicle_id` |
| Booking | auto from context | Required for handover and return kinds | `booking_id` |
| Assigned to | select from `staff_directory` (field) | Required to dispatch | `assigned_to`, `dispatched_by` |
| When | date-time | Required | `scheduled_at` |
| Place | address | Required | `place` |
| Instructions | textarea | Optional | `instructions` |

`createFieldJob` emits `staff_field_job_assigned`. The field staff member sees it from 36 hours before (`field_job_details`).

### 3.3 Photo review (procedures 3 and 4, within 1 hour)

Side-by-side viewer: pickup set and return set in the fixed order, synchronized by shot, with zoom. A missing shot is listed at the top ("Roof and instrument cluster missing"), with "Ask for a re-shoot" (`requestReshoot`: creates a field job and notifies). The reviewer records: new damage (location, type, size, photo number -> `condition_report_damages`, `is_new = true`), kilometres (computed), fuel difference, cleaning grade, minutes late, keys. "Send findings to Finance" (`submitFindings`) sets `condition_reports.reviewed_by` and `reviewed_at`, writes the T7 summary to `messages (template_code = 'T7', audience internal)`, creates the `price_findings` finance task, and for any damage opens an incident and escalates to an admin (the VA never prices damage). After a pickup review, "Mark On Rent" is not a button: the booking is already `on_rent` from the handover; the review only confirms the photo set.

### 3.4 Late returns (procedure 8)

The late panel on a booking shows the clock from the return time and the next step with its time: 0 (call, T13, check tracker, offer extension), 30 minutes (charges start), 2 hours (two calls, T14, tell an admin), 1 hour after T14 (request disable). Buttons: Log call, Send T13 (`renter_late_return_first`), Send T14 (`renter_late_return_final`, stores `notice_sent_at`), Offer extension, Request disable (goes to an admin; `03-admin.md` section 17.1), Open incident. The `late-returns` job sends T13 automatically at 0 and creates the tasks at each step; it never disables a car.

### 3.5 Daily checks (procedure 19)

`/va/fleet/checks`: the opening and closing lists as a form, each line with OK, Problem and a note; lines with data behind them are pre-answered by the system (trackers reporting, jobs acknowledged, tomorrow's pickups verified, T7 sent for every return) and the VA confirms. `saveDailyCheck` writes `daily_checks (check_date, kind, items, issues)`; any Problem escalates.

### 3.6 What Fleet cannot do

Change a vehicle's owner, mode or dates; see licences, ID images or payments; approve a tracker disable; price damage; change rates on a managed vehicle without an admin having set them (Fleet enters, admin sets: `rate_cards` is fleet-writable, and the audit log shows who).

## 4. `/va/cs` Customer Service and Growth

Sections: Queue, Requests (the inbox of `03-admin.md` section 3), Bookings, Calendar (read; create requests), Verifications, Extensions, Cancellations (log), Owners (leads and onboarding to signature), Listings (review and publish), Reviews, Enquiries, Messages.

### 4.1 Requests and offers

The booking review screen of `03-admin.md` section 4 with these limits: no per-booking price override, no approval of outside-Ontario travel, pets or unattended handover (each is an escalation that appears as a pending chip on the offer; the offer cannot be sent until an admin answers), offer expiry up to 48 hours.

### 4.2 Verification screen (procedure 2)

| Element | Detail |
| --- | --- |
| Layout | P: one driver per screen, images stacked, checklist under them. D: licence front, back and selfie side by side with zoom and rotate; the booking's driver details on the right |
| Access | Images open through short-lived signed links; each open is written to `data_access_log`. No download button. The images are not cached by the browser (`Cache-Control: no-store`) |
| Checklist (each is a required tick or a fail) | Name matches the booking; date of birth matches; class is G2 or G (or an accepted equivalent: escalate a non-Ontario licence); expiry is after the return date; the face matches the licence photo; the document shows no sign of alteration |
| Fields the VA types from the licence | Licence number, class, issuer, expiry (pre-filled from what the renter typed; differences are highlighted) |
| Verify | `verifyDriver` -> `identity_verifications (status = 'verified', method = 'staff_review', verified_by, verified_at, checks jsonb)`, `drivers.identity_status`, `booking_drivers.identity_method = 'staff_review'`, `identity_verified_on`; when all drivers are verified, `renters.identity_status = 'verified'` |
| Reject | `rejectDriver` with a reason shown to the renter (photo unreadable, expired, name mismatch) or a private reason for an admin (suspected false document: escalates; procedure 2 step 5) |
| Coverage | For the booking's option: the proof document, the typed details, and ticks: active to the return date; covers this car and every driver (option 1); same card as the Card on File and covers this class and length (option 2). `confirmCoverage` -> `coverage_proofs (status = 'confirmed', confirmed_by, confirmed_at, covers_vehicle_and_drivers)`, `bookings.coverage_confirmed_at`. `rejectCoverage` with a reason |
| Result | When identity and coverage are both done: `renter_identity_approved` (T4). The age fee per driver was applied at the offer; if a date of birth on the licence differs and changes the age band, the VA is told to adjust the booking before verifying |

### 4.4 Finding a customer

There is no customer list. Search box "Find a renter": at least 3 characters; `app.staff_find_renter()` returns at most 10 names; opening one outside the window asks for a reason and calls `app.staff_open_renter()` (24 hours of access, logged in `data_access_log`).

## 5. `/va/sales` Sales (optional role)

Sections: Queue, Quotes, Follow-ups, Calendar (read).

| Capability | Detail |
| --- | --- |
| Create a quote | `/va/sales/quotes/new`: the staff request form (vehicle, dates, places, driver ages, extras, lead's name, email, phone). Creates a `requested` booking through `app.request_booking()` with `source` phone, email or whatsapp and `created_by` the staff member. Sales works only on bookings in `requested` and `offered`, and sees renters' first names on the calendar |
| Send an offer | Same review form; any active assistant may send an offer (`app.send_offer()`). Only the non-refundable 10% saving may be offered; no staff discount (admin only), no override, no promo code creation. An existing promo code may be applied |
| Follow-ups | Offers out, with time left and the last contact. Buttons: Log call, Send a follow-up from approved snippets. A follow-up email is a transactional message about the customer's own quote, not marketing |
| Not available | Payments, refunds, verification images, owners, tolls, anything after confirmation |

## 6. Shared staff behaviour

| Topic | Rule |
| --- | --- |
| Templates | Staff messages use approved templates and snippets; free text is allowed inside them. The coverage provider is never named: a server-side check on outgoing staff messages blocks a configurable list of terms (`13-security.md` section 12) |
| Discounts | The interface has no free discount field for a VA. Only the non-refundable option and an existing promo code |
| Hours | The portals work at any hour; SLA timers count only opening hours from `program_settings.opening_hours` |
| Scorecard | `/admin/staff/[id]/scorecard`: the weekly measures of the VA hiring package section 7, computed from `tasks` (created, due, completed) and the related records. Read-only to the VA for their own |
| Leaving | `endStaffAccess` suspends at once (`03-admin.md` section 16) |
