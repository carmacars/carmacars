# Self-healing: the site fixes its own problems (Release 50: 4800, 4801)

The owner, November 25: "Not just find problems but also create a database of all fixes and find the relevant fixes and apply
them automatically. Self healing. The site does it itself, not Claude on a schedule."

Branch `r50-heal`. Migrations `4800_r50_self_heal.sql` (the engine) and `4801_r50_self_heal_guides.sql` (the guide). DB tests
`supabase/tests/99_r50_heal.sql`; unit tests `web/src/features/self-heal/model.test.ts` and
`web/src/features/api-access/tools.test.ts` (heal_status).

## What it is

| Part | What it does |
| --- | --- |
| The fix library (`heal_playbooks`) | Each fix has a signature (the source: uptime, data_health, site_error, gsc, cron, queue or server; a rule on the key, the message and the state), one action from a fixed whitelist (`heal_actions`) with its params, max attempts, a cooldown, the wait before its check, on or off, and its running success and failure counts. Seeded with 24 fixes from the data health fixes (0441), the recovery jobs (0062) and the incidents in these records: single Error 1102s and pages down (0062, 0075, 0530), the email backlog of November 6 (0530), the id counter left at 1 on the cutover day (0970), the closed database socket on a missing car page (4701), stuck photo renders (r50 photo loops), failing calendar feeds (0062), Search Console 404s on old car pages (1860, 2420), disk, certificates, Caddy, the media server (5010) and a bad deploy |
| Incidents (`heal_incidents`, `heal_attempts`) | One row per problem by its fingerprint: first and last seen, how often, open, healing, healed or escalated; each attempt with its playbook, result, whether the check after it found the problem gone, and the details. Everything is written to `audit_log` |
| The engine (`app.job_heal`, pg_cron `carmacars-heal`, every minute) | Opens and updates incidents from: failing site checks (pages, the backup, Stripe), the data health checks the database fixes itself, error spikes in `client_errors` (12 real errors on one page in 15 minutes), errors right after a deploy, Search Console 404, soft 404 and 5xx pages, failed pg_cron runs (`cron.job_run_details`), emails, texts and push notices stuck sending or an hour overdue, job locks left behind (`job_runs`, `pdf_jobs`, `agreement_jobs`, `photo_jobs`), failing incoming webhooks, calendar feeds failing 3 times, and the server as the heal agent reports it. It runs the matching fix with the best success rate, checks on a later tick that the problem is gone, tries the next fix when it is not, and escalates once |
| Escalation | Once per incident, never again for it: one urgent Admin alert (staff alert rule `self_heal_escalated`), one high To do on the Admin queue and one staff bug report with the evidence (filed as the first Admin, context `filed_by: self-healing`). A problem healed 3 times in 24 hours that comes back is escalated. A healed incident is only a quiet line in Admin > Self-healing; an escalated one that clears on its own closes its To do |
| Circuit breaker | A fix that fails 4 times in a row switches itself off, with one alert (`self_heal_breaker`) and one To do. An Admin switches it on again |
| Money | Never fixed automatically: payments, deposits, payouts, refunds, statements, invoices, charges, commissions, the Stripe check and the money data checks are escalated at once with no attempt. No action touches a booking's money fields |

## The actions (the whitelist)

In the database: run a failed scheduled job again (only a `select app.job_...()` command, never a money job), send stuck
emails, texts and push notices again (at most 5 attempts each, then marked failed), release stale locks and expired request
claims, run the data health fixes and the booking recovery job, read a failing calendar feed again, check the site again,
move an id counter past its highest id (never down), and for a Search Console 404 or soft 404 on a /cars/ page a 301 to the
closest live car (else /cars) through `listing_redirects`, with the page sent to IndexNow and inspected again.

On the server (queued in `heal_requests` for the heal agent): restart the website, Caddy or the media server, renew
certificates, free disk space (journal, dangling images, build cache, old rotated logs), end database connections idle in a
transaction over 10 minutes, and go back to the previous build.

Not built: a feature kill switch per page. The site has no flag system for its pages, and one would mean a database read on
every request; a page throwing server errors gets the restart and, after a deploy, the previous build, and is escalated with
its bug report. Pages outside /cars/ have no redirect mechanism, so their 404s are escalated, not redirected.

## What the site cannot do

It cannot rewrite its own code. For a code bug it mitigates (a retry, a restart, the previous build, a redirect) and files the
bug report with the evidence (the page, the error messages, the counts, what was tried), so a developer fixes the cause.

## The server (infra/vps)

- `infra/vps/bin/heal-agent` with `carmacars-heal-agent.service` and `.timer` (every minute), installed and enabled by every
  deploy-vps deploy (`scripts/deploy/web-vps-remote.sh`, `heal_agent_up`). It reports the build, the build before it, the
  last deploy, the website's health, disk, the certificate, Caddy, the media server and database connections to
  `app.heal_agent_tick` as the role `heal_agent` (it may call that and `app.heal_agent_done`, nothing else), and runs only
  the whitelisted commands by name. Without the database it still restarts a website unhealthy for 5 minutes (once in 15)
  and goes back to the previous build within 30 minutes of a deploy, and reports it later.
- The website and the media server restart always (`restart: always`); the website's image health check decides healthy.
- Automatic rollback: the deploy keeps the build before it (it already kept four images). A new build that never gets healthy
  goes straight back to it and the deploy fails. Within 30 minutes of a deploy, server errors well above the hour before
  (or the container staying unhealthy) make the engine queue `rollback_web`; the agent switches back and the Admins are told
  once, so the bad build is looked at.

## Admin > Self-healing

`/admin/self-healing` (Settings menu, and the Self-healing link on the Site health card): the counts of the week, what needs
you (with what was tried, the bug report, **Resolve** and **Save as fix**), what is being fixed, what was fixed in the last 7
days, the fix library with each fix's success and failure counts and **Switch off** / **Switch on**, and the server's last
report. **Save as fix** turns what fixed an escalated incident into a new fix with the incident's signature and a whitelisted
action. No staff portal other than Admin sees site health, so the page is Admin only. The connector gets the read tool
`heal_status` (admin:read, logged in api_calls).
