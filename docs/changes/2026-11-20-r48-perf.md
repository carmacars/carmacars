# Speed: instant feedback on every tap, streamed portal pages, fewer round trips (Release 48 part PF)

No migration. Branch `r48-pf` (on `r48-int`).

## What was wrong (the owner, November 20, 2026: "so slow rn", the site and every portal)

Measured on a local production build (`next build`, `scripts/serve.mjs`, the local test database; desktop Chromium at
1440 px, median of 3 warm loads; client navigations: median of 3 taps):

- **A tap did nothing until the next page was fully ready.** The portals' links do not prefetch (`prefetch={false}`, 877 of
  them), and no portal page except the renter's trips had a `loading.tsx`, so the old page stayed put with no sign of life:
  Admin To do to Calendar 1,090 ms, Owner home to Money 725 ms, Admin to Bookings 299 ms, home to Cars 354 ms.
- **The servers held every page until its last byte.** `scripts/vps-server.mjs` (the company's server) and `scripts/serve.mjs`
  read the whole HTML to add the nonce to each `<script>`, so even a page with a skeleton showed nothing until its slowest read
  was done.
- **Round trips one after another.** The Admin frame read the gate, then the view-as cookie, then the rail counts, then the chat
  counts (four in a row before any Admin page); the staff frame six in a row (roles, view-as, digest, chat counts, home address,
  live tokens); the Owner home seven (signing checklist, application task, schedule changes, insights, onboarding, each car's
  service, the forecast); the Sales home one extra (call minutes) after the rest. Owner home answered after 1,027 ms.
- **The staff assistant's panel was in every Admin and staff page's JavaScript** although it opens on a tap.
- **The files of `public/`** (logo, favicon, icons, add-on photos, vendored libraries) went out with `max-age=0`: every page
  asked the server again and Cloudflare's proxy never kept them.

Looked at and fine as they are: the public pages are ISR (static, revalidated hourly; TTFB about 30 ms); the photos come
pre-sized from the photo pipeline with `srcset`, `sizes` and lazy loading below the fold; the fonts are self-hosted `next/font`
subsets with `display: swap`; no map, chart, PDF or barcode library is loaded on first paint (they are already loaded on
demand); Caddy compresses (zstd, gzip) and Cloudflare sends brotli; the site-wide public reads are shared across requests in
production (`lib/db/repo.ts` SHARED_READS).

## What changed

### One loader (`web/src/components/loader/`)

- `BrandLoader.tsx` is **the** loader, in one file: the CarmaCars mark pulsing (scale and opacity only), the shimmer block
  (`Shimmer`), the top progress bar's look and a busy button's look. To change how loading looks (the owner's reel), change this
  file only. Its styles are one `<style href="cc-brand-loader">` the root layout puts on every page. Under
  `prefers-reduced-motion: reduce` nothing moves.
- `skeletons.tsx`: the page shapes built from it (dashboard, table, calendar, detail, form, the owner/renter hero, cards; home,
  cars, car page, plain page), and `shapeFor(path)`, which picks the shape for an address.
- `RouteProgress.tsx` (root layout): the moment a link is tapped, the brand-red bar starts; after 140 ms (so a fast page never
  flickers) the page area (`.ad__main`, `.pt__body` or `#main`) shows the skeleton of the page being opened until it arrives. A
  form sent to a server action marks its button busy (`aria-busy`, the loader's ring) until the action answers (it counts the
  `Next-Action` fetches). It only watches: no link or form behaves differently, and everything clears by itself after 15 s.
- The busy-button rule moved from `styles/core.css` to the loader.

### Every portal page has a skeleton shaped like it

- A `loading.tsx` for each page of Admin, staff (Sales, CS, Fleet, Finance, Field), Owner and renter (280 files, each one line:
  `<PageSkeleton shape="table"/>`), so a page shows its frame and its skeleton while its data loads.
- Not for the pages that only redirect (29: the parent's skeleton covers them).
- Not for the public pages and the investor portal, deliberately: a page under a `loading.tsx` streams its skeleton first, so its
  status is decided before the page runs; a missing car or place page would answer 200 with the not-found page (a soft 404 for
  search engines) and a moved page would redirect inside the page instead of with a 307. The portals are noindex, so there it is
  fine; the public pages get the same instant skeleton from `RouteProgress` on every tap instead.
- `app/not-found.tsx` carries `data-page="not-found"`; `tests/lint/crawl-roles.mjs` reads a portal's in-stream not-found as a
  404 and follows an in-page redirect, so the crawl still finds a broken portal link.
- `tests/e2e/consolidation.spec.ts`: Customer service on `/staff/marketplace` now checks the not-found page instead of the 404
  status, for the reason above.

### The HTML streams (`web/src/lib/security/nonce-stream.ts`)

- `scripts/vps-server.mjs` and `scripts/serve.mjs` add the nonce while the page streams through (a `<script` split between two
  pieces is held back until whole; unit tested at every split point), so the frame and the skeleton reach the browser before the
  slowest read. The kept copy of a public page (stale-on-error) is still taken from the whole page once it has streamed. The
  headers (policy, cache, region cookie) are the same; the page goes out chunked instead of with a length.

### Fewer round trips

- Admin frame (`app/admin/layout.tsx`): the gate with the view-as cookie, then the rail counts, the chat counts and the live tokens
  together.
- Staff frame (`app/staff/layout.tsx`): roles with view-as, then the digest, the chat counts, the home address and the live tokens
  together.
- Owner home (`app/owner/page.tsx`): its seven reads in one `Promise.all` after the owner check.
- Sales home (`app/staff/page.tsx`): the call minutes with the other reads.

### Less JavaScript on every Admin and staff page

- `features/assistant/AssistantLauncher.tsx`: the header shows the Assistant button alone; the panel (`AssistantPanel.tsx`) loads
  the first time it is opened (the button or Ctrl+/), or when the pointer rests on the button, and opens at once. About 13 kB
  (compressed) less on every Admin and staff page.

### Static files cached

- `next.config.ts` headers: `public/` logos, icons, favicons, add-on and plate images, OG images, guide images, the live map's data
  and pdf.js: a day in the browser and at Cloudflare, then served stale while refreshed (30 days); the versioned libraries under
  `/vendor` (maplibre-gl-4.7.1, twilio-voice-sdk-2.18.5, zxing-wasm-3.1.6): a year, immutable. The service worker and the manifest
  keep their own rules.

## Before and after

The machine is shared with other builds and was busier during the after run (load average about 8 on 2 cores), so the after run
is slower across the board: the public pages, whose code did not change, went from 27 to 60 ms TTFB. What changed in kind is the first feedback.

| | before | after |
|---|---|---|
| Tap to first feedback (bar or skeleton): Admin to Calendar, Admin to Bookings, Owner to Money, home to Cars | 1,090 / 299 / 725 / 354 ms (= the whole page) | 19 / 16 / 17 / 24 ms |
| Owner home, full load: TTFB / first paint | 1,027 / 1,276 ms | 117 / 364 ms (skeleton; content at about 1.9 s under load) |
| Admin To do: TTFB / first paint | 338 / 612 ms | 234 / 540 ms |
| Admin bookings: TTFB / first paint | 167 / 368 ms | 263 / 496 ms (load) |
| Sales home: TTFB / first paint | 366 / 688 ms | 617 / 896 ms (load) |
| Admin calendar: TTFB / first paint | 604 / 972 ms | 938 / 1,344 ms (load) |
| JS on an Admin page (compressed) | 239 kB | 240 kB: the assistant out (13 kB less), the loader and bar in (3 kB more), the bug report dialog now a chunk of its own |
| Public pages (home, car, cars): TTFB, JS, images | 27 to 34 ms, 183 to 197 kB, 19 to 127 kB | unchanged code; same sizes |

## Not done here (left for later, on purpose)

- The heaviest database reads behind the portals: `calendar` (about 230 ms alone, 83 kB for 20 cars), `fleet_availability`,
  `admin_todo`, `dashboard`, and `site_facts` (about 340 ms; shared across requests in production). They are layered SQL
  functions (`door` passes through about 25 wrappers); rewriting them needs a migration and production-sized data to measure.
  No index is clearly missing at the local data size.
- Prefetching portal links on hover: it would render each hovered page's frame on the server; the skeleton already gives the
  feedback.
- The `/cars` HTML is about 760 kB before compression (61 kB compressed): the cards' markup, worth a look on its own.
- The calendar's car list is not virtualised: with the current fleet it renders fine; worth it past about 150 cars.

## Guides

No guide change: the pages look and behave the same, they only load faster and show a loader while they do.
