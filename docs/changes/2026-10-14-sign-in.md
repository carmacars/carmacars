# Sign-in for every portal, October 14, 2026

The owner reported that sign-in to the portals was not working. This record is what was found, what changed, and the
live results. Database record: `docs/changes/0036_sign_in.md`.

## 2. Sign-in, landing and refusal

- After the password: the page asked for (`?next=`, a path on this site only), else the person's portal: Admin
  `/admin`, staff `/va`, field `/field`, investor `/investor`, owner `/owner`, renter `/account`. Two or more portals:
  `/choose-portal` (one button each; a staff member with several functions gets one per function). Renting counts only
  when there is nothing else. Two-step sign-in comes first as before.
- Every portal's frame lists the account's other portals ("Also: ...").
- Refusal pages (`/admin/no-access`, `/va/no-access`, `/field/no-access`, `/investor/no-access`,
  `/owner/not-an-owner`) say "You are signed in as ...", list the account's portals and offer Sign out. For an Admin
  they point to Admin > Portals.
- Sign-in errors: "That email and password do not match an account" for both an unknown address and a wrong password,
  with "Invited by CarmaCars and never chose a password, or forgot it? Set a new password"; an unconfirmed address
  says so with "Send the confirmation link again"; too many tries says to wait a minute.
- Reset and invitation links: one hour (the project's single setting for all email links; kept). An expired or used
  link lands on `/link-expired`, which sends a new one in one step, with the address asked from this device filled in.

## 3. View as

An Admin opens any portal as one of its people: Admin > Portals lists every portal (Admin, the staff portal per
function, field, owner, investor, renter) with "Open as this person" and a link to that portal's sign-in page; Admin >
Staff, Owners and Investors have "View as" on each row.

- `POST /api/view-as/start`: the Admin is checked, then the database (`app.view_as_start`) checks the person, the portal
  and the function, and writes the start to the audit log.
- The choice is a cookie signed with `LINK_SIGNING_KEY`, httpOnly, 30 minutes, naming the Admin. It counts only while
  that Admin is signed in and still an Admin (checked on every request, with two-step sign-in when it is required). A
  copied cookie is worth nothing to anyone else (tested).
- Reads use the person's identity: their row-level security reads go with a 5-minute token made on the server
  (`SUPABASE_JWT_SECRET`, the project's legacy HS256 key, which the database API still accepts), staff and investor
  reads go through the door as them.
- A red banner on every page: "Viewing as Name (email), read only." with Exit (`POST /api/view-as/exit`). In `/admin`
  the Admin is always themselves; the banner says so.
- Every write is refused, centrally: the Worker entry refuses any request other than GET outside `/admin` while the
  cookie is set (a server action is sent to `/read-only`, anything else gets 403), and the database layer refuses any
  call made for that person that is not a read (`refusedForViewAs` in `src/server/view-as.ts`, used by `rpc()` and the
  door). Tested in `src/lib/auth/session.test.ts`, `tests/e2e/signin.spec.ts` and live.

## 4. Invitations and password links

- Admin > Portals: invite into any role: Admin, staff (main function and the functions covered), field staff, an
  owner on file, an investor on file. Admin > Staff: the staff roles. Admin > Owners and Investors: one click for a
  record without a sign-in.
- The invitation is Supabase's branded invitation email (`scripts/deploy/auth-templates.mjs`), linking to
  `/auth/callback?token_hash=...&type=invite&next=/update-password`; after the password the person lands in their
  portal. Someone who already signs in gets the role and no email.
- "Send password link" on every account (Portals, Staff, Owners, Investors): the branded reset email, one hour.
  Recorded in the audit log.

## 5. For the owner: getting into Admin

1. Go to https://carmacars.ca/reset-password
2. Enter `rent@carmacars.ca` and press "Send the link".
3. Open the email "Reset your CarmaCars password" within one hour and press "Choose a new password".
4. Choose a password (8 characters or more) and press "Save the new password". You land in Admin.
5. Next time, sign in at https://carmacars.ca/sign-in with that address and password.

If the link has expired, the page it opens has "Send me a new link". Admin > Portals then opens every other portal.

## 7. Worker CPU

Changes that cut work per portal page:

- Who is signed in is read from the session cookie and the access token verified with the project's published key
  (one WebCrypto check). Before, every page built a Supabase client (Auth, Realtime, Storage and Functions sub-clients)
  and asked Supabase Auth for the user, the session and the assurance level. supabase-js is no longer loaded to render
  a portal page at all (only sign-in, sign-out and two-step load it).
- Every Admin page drew the whole dashboard (every list, the fleet's days this month, the setup checks) for the five
  numbers on the rail; it now reads those five counts (`admin_rail_counts`).
- The renter and owner frames read 100 whole notices to count the unread ones; they now read the count.

## 8. Still open

- **Workers Paid plan**: the owner's step in the Cloudflare dashboard (Workers & Pages > Plans). Nothing in the code
  changes.
- **CPU per path**: give the `CLOUDFLARE_API_TOKEN` secret "Account Analytics: Read", "Workers Observability: Read" and
  the zone's "Analytics: Read"; the verify run then reports CPU p50/p99 and 5xx answers per path with no code change.
- **Email links last one hour.** Supabase has one setting for every email link (`mailer_otp_exp`); it stays at one
  hour. An expired link offers a new one in one step.
- **View as of the renter and owner portals** reads with a token made from the project's legacy JWT secret, which
  Supabase still accepts (it is listed as "previously used" beside the current ES256 key). If that legacy key is ever
  revoked in the Supabase dashboard, those two views stop (the staff, field and investor views do not depend on it).
- **Ending a staff member's access** (Admin > Staff > End access) closes their portal on the next page (the database
  checks the account's status on every read); their sign-in itself is not revoked at Supabase. The button's message
  said "signed out of every session", which was not so; it now says the staff portal closes to them at once.
- **The reset form under a headless browser**: the bot check stops it, so the live run checks the link and the
  password page but not the form's button.
