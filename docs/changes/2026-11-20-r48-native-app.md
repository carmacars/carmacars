# The native CarmaCars app for iPhone and Android (Release 48: 3170)

Migration `3170_r48app_passkeys.sql`. App: `apps/carmacars-native`. API: `/api/m/v1`. Owner's steps:
`docs/apps/native-publish.md`.

The first app (`apps/carmacars`, decision 0002) was a shell around the website. The owner rejected it: Apple refuses
apps that are a website in a frame (guideline 4.2), and it felt like a website. This is the replacement: native screens
in Expo and React Native, talking to the site through a small JSON API. The first app was never submitted; its folder
stays for now because the store listing texts and graphics live there and both apps use them.

## What the app does

One app for every role; the tabs are what the account holds (`src/logic/roles.ts`).

- **Renter.** Cars with the site's filters (type, seats, make, model family, transmission, daily rate) and, with dates,
  only the free cars at the price for those dates; a car's page with its photos to swipe; request to book in three steps
  (the site's own request, checked again by the site's schema and the database); the offer (accept, ask for a change,
  decline); the agreement, read and signed on the phone; payment with the processor's own payment sheet; licence front
  and back and a selfie with the camera; check in at the car and check out when it is returned (photos, dashboard,
  odometer, fuel, selfie); extend; messages; phone alerts.
- **Field staff.** Today's shift and jobs, open shifts to claim, clock in and out with the phone's location (or the
  reason, which the database asks for away from the lot), and the handover checklist: each required photo with the
  camera, odometer, fuel, keys, cleanliness, damage with its photo, the licence and card checks, both signatures.
- **Sales.** The lead pool and my leads, claim, the lead with its history, call and text through the platform (the app
  only ever holds the masked number it was shown; the server finds the real one), notes and outcomes, and a simple offer
  at the rate sheet's price.
- **Owner.** My cars with what each is doing now, the month so far, the bookings of my cars, statements.
- **Admin, investor and everything else.** Opens on the site in the browser inside the app (Safari or Chrome's own
  sheet), as the owner agreed.
- **Every account.** Sign in with email and password, a texted code or a passkey; two-step sign-in for staff; app lock
  with Face ID, fingerprint or the passcode after five minutes away; alerts and their topics; delete my account, started
  in the app; an offline bar, with what was last loaded still on screen; links to carmacars.ca (universal links, app
  links, `carmacars://`, tapped alerts) open the matching screen.

Brand: red, black and white, the CarmaCars mark on the splash and the lock screen. Motion is a short fade and rise on
arriving content; with Reduce Motion on in the phone's settings nothing moves (`src/ui/kit.tsx`).

## The mobile API (`/api/m/v1`)

`web/src/features/mobile-api/contract.ts` is the table of routes, shared by the site and the app (the app's bundler and
TypeScript read the file from `web/`, so there is one copy). `web/src/app/api/m/v1/[...path]/route.ts` is the door;
`web/src/server/mobile/routes.ts` holds the handlers.

The API adds no rule of its own. The door checks the access token (`Authorization: Bearer`, the same token the website
keeps in its session cookie) and runs the handler inside a call context (`web/src/server/mobile/context.ts`). The
sign-in adapters read the token from that context, so a handler is one line: it calls the server action, the read or
the existing route the website already uses for the step, and that code finds the signed-in person exactly as it does
for a browser. The same database functions make the same checks and refuse in the same words, and the same audit trail
is written: a signature made in the app goes through the site's signing session (migration 0154) with the document's
SHA-256, each step, the address and the phone's name.

- **Open routes (11):** `config`, `cars`, `cars/available`, `cars/:slug`, `cars/:slug/quote`, `auth/sign-in`,
  `auth/refresh`, `auth/phone/start`, `auth/phone/verify`, `auth/passkey/options`, `auth/passkey/verify`.
- **Account:** `auth/two-step`, `auth/sign-out`, `me`, `me/name`, `me/passkeys` (list, options, add, remove),
  `me/deletion` (ask, withdraw), `me/push` (on, off, test, topics), `notices`, `notices/read`.
- **Renter:** `trips`, `trips/:number`, `.../messages`, `.../offer`, `.../agreement`, `.../esign`, `.../sign`,
  `.../payment`, `.../payment/finish`, `.../uploads`, `uploads/confirm`, `.../licence`, `.../checkin/photos`,
  `.../checkin`, `.../return/photos`, `.../return`, `.../extension/preview`, `.../extension`, `.../extension/:id/pay`,
  `.../cancellation`, `requests`, `requests/account`.
- **Field:** `field/today`, `field/jobs`, `field/jobs/:id`, `field/jobs/:id/photos`, `field/shifts`, `field/act`,
  `field/clock`.
- **Sales:** `sales/leads`, `sales/leads/:id`, `sales/leads/act`, `sales/phone`, `sales/offers/read`, `sales/offers`.
- **Owner:** `owner`, `owner/bookings`, `owner/statements/:id`.

Security decisions (the ones marked are held by `web/tests/e2e/mobile-api.spec.ts` or the contract's unit test):

- No cookie is ever read in a mobile call. A browser on another site has nothing to send, and the cross-site check of
  every request still runs first. Signing in through the API sets no cookie. (Tested.)
- A bearer token sent to any address outside `/api/m/v1` is ignored: only the door sets the call context.
- The steps the app may take are named in the contract. A field step, a lead step or an offer step outside the list
  (the licence review, reassigning leads, recording payments) is refused before the server action is reached. (Tested.)
- The two things a signed-out phone can send (a sign-in code by text, a request to book) keep the website's bot check.
  The app opens the site's own check in a small sheet (`/app-check`, kept out of search) and sends its token with the
  request; the server verifies it as it does for the website's forms. No check was loosened for the app. (Tested.)
- Sign-in keeps the website's limits and records: the pause after many wrong passwords, the sign-in event, the limits
  on texted codes.
- An app older than the server can work with is told to update (HTTP 426) before anything else. (Tested.)

## Passkeys (migration 3170)

New on the platform; the website has none yet. Tables `passkeys` and `passkey_challenges` (row-level security, Admins
only by policy, nothing for a browser role), and seven functions the server alone may call. The phone keeps the private
key; the site keeps the public key. `web/src/lib/auth/webauthn.ts` checks the phone's answer with WebCrypto only (no new
package): the challenge, the site's domain, the origin (the website for the iPhone app, the signing certificate's hash
for the Android app), the screen-lock flag and the signature. The database decides the rest: a challenge is random,
lasts five minutes and works once; a passkey is added only by the signed-in person, at most ten each, never twice; a
counter that does not move forward is refused (a copied key); thirty challenges in five minutes from one address is the
limit. After a passkey checks out, the session is issued by the sign-in service through a one-time link made and used on
the server and never sent anywhere. An account made by phone with no email adds its email before it can use a passkey.

## Builds

`.github/workflows/apps-native.yml`: run on demand only, never on a push. It installs the app, runs its checks
(`npm run check`, the type check, the unit tests), makes the native projects with `expo prebuild` and builds with
fastlane (`apps/carmacars-native/fastlane/Fastfile`): a signed App Bundle for Android, an archive signed with the App
Store Connect API key for iPhone, optional upload to the testing tracks, optional upload of the listing texts from
`apps/carmacars/store`. No paid build service. The secrets are the ones the first app's workflow named. The Android
upload key was not generated here: the helper that built this has no access to GitHub's secrets, so
`docs/apps/native-publish.md` step 5 gives the one command and where its result goes.
