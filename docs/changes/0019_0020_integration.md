# 0019 and 0020: integration

Migrations `0019_booking_app.sql` and `0020_operations.sql` were written in parallel and merged into main one after the other. Neither has been applied to a real database, so both were edited to give one design. 0020 runs after 0019; where an object belonged to both, the one definition now lives in the migration that owns the data it works on, and the other file uses it.

## How the overlaps were found

Every function, table, view, column, trigger, policy, index and check constraint created, replaced or changed in each file was listed and the two lists intersected. The objects defined in both files were: `bookings.deposit_waived_at`, `deposit_waived_by`, `deposit_waived_cents`, `app.waive_deposit`, `app.user_va_has`. The lists were then read side by side for the same thing under two names (settings, columns, task types, checks). No table, view, policy name on the same table, trigger name or index is shared.

## Left as they are (not duplicates, noted for a later change)

- Extensions made from the calendar: 0020's `app.calendar_apply_change()` inserts a `requested` extension with its own price (rental difference plus HST), while 0019's `app.request_extension()` prices through `app.preview_extension()` (fee lines too). Both use one table, one open-extension index and one review task, and 0019's approve, pay and lapse functions handle either row.
- Changes to a confirmed booking from the calendar: 0020's `renter_approval` path raises `booking_change_approval` and applies the change once the renter agreed; 0019's `booking_change_requests` hold renter requests and staff proposals. Both coexist without conflict; routing the calendar path through `booking_change_requests` would be one flow.
