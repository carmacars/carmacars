# Every AI feature at no cost on the company's server (Release 48: 3095)

Migration 3095. Owner decision, November 16: once the site moves off Cloudflare Workers this release, every AI feature
must keep working at zero cost. docs/hosting/off-cloudflare.md, section 2.2.

## The chain

Every AI call of the site goes through one chain (`web/src/integrations/ai/chain.ts`); a link that answers quota,
unavailable, timeout or invalid output hands the call to the next one:

1. **Workers AI** over its REST API (or the Worker's binding while the Worker still serves): the free 10,000 neurons a
   day, still behind the usage guard (`guard.ts`, `paused.ts`, migration 0133's tiers). Never past its share: the guard
   answers quota and the chain moves on.
2. **The server's own models** (`infra/vps/ai`), free and private (nothing leaves the server), CPU only:
   - text: Ollama in `carmacars-llm`, **Qwen2.5 3B Instruct** (Q4_K_M, digest `357c53fb659c`), JSON through Ollama's
     structured outputs; at least 60 s a call (`web/src/integrations/llm/local.ts`);
   - vision: the same container, **Qwen2.5-VL 3B** (digest `fb90415cde1e`), the image made 768 px first; at least 90 s
     (`vision/local.ts`);
   - speech: whisper.cpp's server in `carmacars-stt`, **Whisper small.en**, built from the pinned tag v1.7.6 on the
     server, its model checked against the published SHA-1 `db8a495a…` (`transcribe/local.ts`).
   A model is used only when Ollama reports the pinned digest; another digest is removed by the warm-up.
3. **Gemini's free tier**, for what is not private only. Never: driver's licences and permits (`licence_read`,
   `permit_read`), recordings (`interview_transcribe`, `call_transcribe`) and the text made from them (`phone_summary`,
   `interview_followup`, `interview_score`). Gemini is no longer held by Workers AI's guard (it spends no neurons, and is
   the fallback when that allowance is used); its own 429 is a quota answer.

With no link at all the call answers as before (the fake on a local server; "not connected" for speech). The staff
assistant has its own chain: Workers AI within the assistant's share, the local model, then Claude only within the
budget an Admin allows (US$0 by default).

**The database's gates** (`app.ai_allow`, which every AI gate asks) let a feature run past Workers AI's share while a free
provider that may serve it is ready: the server's model of its kind (seen within 15 minutes by the five-minute heartbeat
`/api/jobs/ai-local`, on the server's tick only), or Gemini for a feature that is not private. Not for a feature whose
route is "Workers AI only". So call transcripts, interview scores and the photo checks no longer wait for tomorrow.

**Admin > Settings > Usage, "AI providers by feature"**: each feature's order (auto; never Gemini; the server first;
Workers AI only; the server only; a private feature never offers Gemini), the provider of its last call, its calls of the
last 7 days by provider and its failures, and the server's models: ready or warming up. Every call is recorded
(`app.ai_served`, 30 days) by the chain, the assistant and the listing photos' direct Gemini reads.

## Workers AI without a new secret

`deploy-vps` runs `scripts/deploy/workers-ai-cred.mjs`: the `WORKERS_AI_API_TOKEN` secret when it works; else a token
with **Workers AI Read only**, made by the CI token (needs Account > Account API Tokens > Edit on it; the two newest of
that name are kept); else nothing. The CI token `CLOUDFLARE_API_TOKEN` itself is never written to the server. Each is probed
with one call to a 1B model (one output token). The job summary says whether Workers AI is on; when no token may run it,
it names the permission to add: **Account > Workers AI Read**. The deploy never fails for it.

Security: the CI token may also edit DNS and Workers, so it never goes on the internet-facing server. Without a
`WORKERS_AI_API_TOKEN` secret or "Account API Tokens > Edit" on the CI token, the server has no Workers AI and answers from
its local models; the job summary says so and names the permission to add.

## The server: memory and CPU budget (VPS-4: 8 vCPU, 24 GB)

| Container | Memory cap | CPU cap | CPU weight |
|---|---|---|---|
| Supabase stack (Postgres 6 GB shared buffers, API, auth, storage, Caddy) | none: about 13.5 GB always left to it | none | default (1024) |
| `carmacars-web` | 3 GB | none | default |
| `carmacars-llm` (one model loaded at a time, two calls at once, 8k context) | 6 GB | 4 CPUs (4 threads a call) | 256 |
| `carmacars-stt` | 1.5 GB | 2 CPUs | 128 |

The AI containers are the first the kernel stops if memory ever runs out (`oom_score_adj` 800), have no published
port (the Supabase network only), and drop privileges. The warm-up (`infra/vps/ai/warm.sh`) runs as a systemd unit at
nice 19 with idle I/O: it pulls and checks the models, removes unpinned ones, builds and starts whisper. A deploy starts
it and never waits: the summary says "warming up" until the state file says ready.
